# SCADA: руководство администратора по доступу

Документ для администратора безопасности и ведущего инженера объекта. Модель прав и порядок публикации описаны
в документе «SCADA: модель прав и публикация конфигурации». Здесь — как это настроить и обслуживать.

## 1. Модель в двух словах

- **Право** — одно действие: просмотр, квитирование, команды, публикация и т. д. (11 кодов, см. раздел 3).
- **Роль** — именованный набор прав. Шесть системных ролей даны, свои создаются копированием.
- **Область** — узел дерева объектов: Установка → Водоотведение → КНС-1. Назначение действует на узел и всё вложенное.
- **Назначение** — «кто (пользователь или группа AD) + роль + область + срок». Права складываются, запретов нет.
- Права «Пользователи» и «Аудит» действуют только при назначении на корневую область.
- Устройство, тег и схема принадлежат одной области. Тег без своей области — в области устройства, тревога — в области тега.

Пользователи, роли, области и назначения меняются **сразу**, без черновика, и пишутся в аудит с составом прав до и после.
Принадлежность объектов к областям — часть конфигурации: меняется в черновике и вступает в силу после публикации.

## 2. Первый запуск и переход с прежней версии

1. Примените миграции по порядку: `001_schema.sql`, `004_publication.sql`, `005_access.sql`
   (`deploy/install.sh` и `docker-compose.yml` делают это сами; скрипты идемпотентны).
2. Миграция `005` создаёт корневую область «Установка» и переносит в неё все объекты.
   Прежние роли становятся назначениями на корень:

   | Было | Стало |
   |---|---|
   | viewer | Наблюдатель |
   | operator | Оператор |
   | engineer | Инженер |
   | admin | Администратор безопасности + Инженер |

   Записываемые теги получают класс «Обычный». Текущая конфигурация уже сохранена как версия 1.
3. На пустой базе при первом старте создаётся `admin` (Администратор безопасности + Инженер, пароль из
   `Scada__InitialAdminPassword`, смена при первом входе).
4. Постройте дерево областей: «Доступ → Области». Затем инженер переносит устройства и схемы в свои области
   (поле «Область» в формах) и публикует.
5. Разнесите обязанности: снимите с `admin` роль «Инженер», если инженеры работают под своими учётными записями.

## 4. Классы критичности команд

Класс задаётся в форме тега («Запись из SCADA → Класс критичности») и меняется только через публикацию.
Понижение класса попадает в предупреждения проверки и выделяется в списке изменений.

| Класс | Нужное право | Подтверждение |
|---|---|---|
| Обычный | «Команды» (дискретные) или «Уставки» (аналоговые) | Диалог с текущим и новым значением |
| Важный | то же | Диалог + повторный пароль + комментарий |
| Критичный | «Критичные команды» | Пароль + комментарий + второй пользователь с тем же правом за 60 с |

- Второй подтверждающий — **другой пользователь с другого сеанса**. Это проверяют веб-приложение, триггер БД
  (`command_confirmations`) и служба сбора перед записью в ПЛК.
- Срок жизни команды (15 с) отсчитывается от второго подтверждения. Не подтверждённая вовремя команда истекает и
  не исполняется никогда.
- Объект с одним дежурным: `Commands__CriticalConfirmMode=permit` — вместо второго пользователя повторный пароль
  и номер наряда-допуска. Решение принимает заказчик, номер наряда пишется в аудит.
- Защиты и блокировки остаются в ПЛК. Класс в SCADA не заменяет блокировку в программе контроллера.

Параметры в `/etc/scada/scada.env`:

```
Commands__TtlSeconds=15
Commands__ConfirmSeconds=60
Commands__CriticalConfirmMode=second_user   # или permit
```

## 5. Active Directory

### Подключение

```
Directory__Enabled=true
Directory__Servers__0=dc1.vodokanal.local
Directory__Servers__1=dc2.vodokanal.local
Directory__Port=636
Directory__BaseDn=DC=vodokanal,DC=local
Directory__BindDn=CN=svc-scada,OU=Service,DC=vodokanal,DC=local
Directory__BindPassword=…
Directory__RefreshMinutes=15
Directory__OfflineGraceHours=8
```

- Только LDAPS (636). Порт 389 служба отвергает при старте.
- Служебная запись — только чтение каталога.
- Сертификат контроллера домена должен быть доверенным для сервера SCADA: корневой сертификат домена положите
  в `/usr/local/share/ca-certificates/` и выполните `update-ca-certificates`.
- На Linux нужна библиотека OpenLDAP: `apt install libldap-2.5-0` (Debian/Ubuntu) или `dnf install openldap` (RHEL).

### Сопоставление групп

«Доступ → Назначения и группы AD → Сопоставить группу AD»: имя группы (cn), роль, область. Вложенные группы
учитываются (правило `LDAP_MATCHING_RULE_IN_CHAIN`). Пример:

| Группа AD | Роль | Область |
|---|---|---|
| SCADA-Operators-KNS | Оператор | Водоотведение |
| SCADA-Senior-Operators | Старший оператор | Водоотведение |
| SCADA-Engineers | Инженер | Установка |
| SCADA-Viewers | Наблюдатель | Установка |
| SCADA-Security | Администратор безопасности | Установка |

Кнопка «Прочитать группы из AD» показывает, какие группы видит SCADA у указанного логина, — первое, что
проверять, если у пользователя «нет назначенных прав».

### Как это работает

- Вход: поиск пользователя служебной записью, проверка пароля привязкой (bind). Пароль в SCADA не хранится.
  При первом входе создаётся запись с ФИО из AD.
- Итоговые права = сопоставления групп пользователя + его личные назначения в SCADA.
- Группы перечитываются каждые 15 минут. Отключённая или удалённая в AD запись теряет сеанс при ближайшей
  проверке (событие `session_revoked` в аудите). Перед важной и критичной командой группы проверяются заново.
- AD недоступен: вошедшие работают с последними известными правами до 8 часов, новый вход доменной записью
  невозможен.

### Аварийные учётные записи

Держите 1–2 локальные записи оператора с флажком «Аварийная запись» («Доступ → Пользователи»).
Каждый вход под ними пишется в аудит отдельным событием `emergency_login`, а на всех АРМ с правом «Аудит» или
«Пользователи» появляется оповещение. Пароли аварийных записей храните в опечатанном конверте у начальника смены.

## 6. Типовые задачи

| Задача | Где |
|---|---|
| Принять оператора на КНС-3 | Добавить в группу AD или «Пользователи → Назначения → Выдать роль»: Оператор, область КНС-3 |
| Подрядчик на пусконаладку | Локальная запись + Наладчик на область объекта со сроком «Действует до» |
| Уволить сотрудника | Отключить в AD (сеанс завершится в течение 15 минут) или сразу — флажок «Активен» в SCADA |
| Инженер не может опубликовать | В «Публикации» у изменения видна метка «нет права на публикацию» и области — нужна «Публикация» на них |
| Оператор не видит схему | Схема в области, на которую у него нет «Просмотра»; элементы с тегами чужой области показывают «нет данных» |
| Проверить, кто что сделал | «Аудит»: у команд — класс, способ подтверждения, второй подтверждающий; у назначений — права до и после |

## 7. События аудита

| Событие | Когда |
|---|---|
| `login`, `login_failed`, `logout`, `session_revoked` | вход, ошибка входа, выход, сеанс прекращён (отключён в AD/SCADA, истёк офлайн-период) |
| `emergency_login` | вход аварийной локальной записью |
| `access_denied` | не хватило права: какое право и на какую область |
| `role_change`, `assignment_change`, `area_change`, `user_change` | изменения доступа с составом прав до и после |
| `command_requested`, `command_confirm`, `command`, `command_denied` | критичная команда ждёт подтверждения; подтверждение/отклонение; результат; отказ (пароль) |
| `config_publish`, `config_rollback`, `draft_discard`, `publish_denied` | публикация, откат, сброс черновика, отказ (ошибки проверок или нет права на области) |

Журнал только дописывается и связан цепочкой хешей; целостность проверяется кнопкой в разделе «Аудит».
